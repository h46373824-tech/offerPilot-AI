## 2. 产品背景

校招信息分散在企业官网、招聘平台、公众号、院校就业网和个人表格中。求职者往往需要同时处理岗位筛选、截止日期、投递材料、笔试、面试和 Offer 决策，容易出现信息遗漏、重复投递、错过截止时间以及难以复盘等问题。

OfferPilot AI 的第一阶段目标是建立统一、清晰、可运行的求职管理底座。平台优先解决“信息集中”和“流程可追踪”，为后续在可信数据与用户授权范围内加入智能匹配、简历建议和投递复盘能力打基础。

## 3. 产品目标

### 3.1 第一阶段目标

1. 让用户在一个工作台中浏览演示企业和岗位并管理收藏。
2. 让用户完整记录从准备投递、已投递、笔试/面试到 Offer 的个人进度。
3. 用日历、统计指标和图表帮助用户识别即将截止事项并复盘投递表现。
4. 建立可扩展的认证、API、数据库、迁移、测试和容器化基础。
5. 清晰区分演示数据、用户录入数据与未来经核验的外部数据，避免误导。

### 3.2 非目标

第一阶段不承诺：

- 实时覆盖全网校招信息；
- 自动替用户投递或操作第三方网站；
- 绕过验证码、登录限制、反爬机制或网站条款；
- 对录用概率、薪资或企业真实性作保证；
- 接入大模型后自动生成招聘事实；
- 企业端招聘管理、多租户或商业计费；
- 生产级消息推送、简历解析或自动推荐。

## 4. 用户画像

### 4.1 主要用户：2027 届校招生

- 同时关注多个行业、城市和学历门槛；
- 每周处理多条岗位、网申、笔试和面试信息；
- 希望减少维护表格的成本并及时看到截止日期；
- 需要在不同设备上快速查看进度；
- 对招聘信息的准确性和来源透明度敏感。

### 4.2 次要用户：项目维护者

- 维护企业、岗位和演示数据；
- 通过 OpenAPI 验证接口；
- 管理数据库迁移、测试和部署；
- 为未来经授权的数据导入与核验流程提供基础设施。

## 5. 核心使用场景

### 场景 A：建立求职账号

用户使用姓名、邮箱和不少于 8 位的密码注册。注册成功后获得访问令牌并进入工作台；再次访问可以通过邮箱和密码登录。

### 场景 B：筛选企业与岗位

用户通过关键词、行业、城市、学历、岗位类别等条件缩小范围，查看明确带 Demo 标识的演示数据。任何演示截止日期只用于产品体验，用户不能把它当作真实招聘事实。

### 场景 C：管理求职漏斗

用户收藏感兴趣岗位，创建投递记录并更新状态；收到面试或 Offer 后继续记录安排、地点、备注和决策截止日期。

### 场景 D：查看时间与风险

用户通过校招日历和 Dashboard 看到即将截止岗位、近期面试或 Offer 决策事项，减少遗漏。

### 场景 E：复盘求职表现

用户查看投递趋势、行业分布、投递到面试的转化表现和最近投递记录，调整时间分配。第一阶段的前端图表包含演示展示，个体统计以 API 中当前用户的记录为数据边界。

## 6. 功能范围

### 6.1 身份认证

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| AUTH-01 | 用户注册 | 校验合法邮箱、姓名和至少 8 位密码；邮箱已存在返回冲突错误 |
| AUTH-02 | 用户登录 | 正确凭据返回 JWT；错误凭据不泄露账户细节 |
| AUTH-03 | 当前用户 | 携带 Bearer Token 返回当前用户基础信息 |
| AUTH-04 | 密码安全 | 数据库只存 Argon2 哈希，不存明文密码 |
| AUTH-05 | 访问控制 | 企业/岗位读取公开；个人资源要求认证并按 `user_id` 隔离；主数据写入限管理员 |

### 6.2 页面与导航

| 页面 | 主要能力 |
| --- | --- |
| 登录页 | 邮箱、密码登录；显示请求中和错误状态；跳转注册 |
| 注册页 | 姓名、邮箱、密码注册；成功后进入工作台 |
| Dashboard | 8 项指标、2 类图表、最近投递记录 |
| 企业库 | 企业列表、关键词检索、行业/学历筛选入口、Demo 状态 |
| 岗位库 | 岗位列表、关键词检索、类别/城市/学历等筛选入口、收藏入口 |
| 投递管理 | 展示和管理个人投递阶段与进度概览 |
| 校招日历 | 按截止日期展示事项，并突出即将截止状态 |
| 收藏 | 展示当前用户收藏的岗位并提供详情入口 |
| Offer 管理 | 展示 Offer 状态、地点、薪酬备注与决策截止信息 |
| 数据分析 | 投递/面试分布、转化指标与周期概览 |
| 设置 | 个人资料、毕业年份、学历、目标城市和通知偏好界面 |

全局界面包括左侧导航、顶部搜索入口、通知入口、深色模式、移动端抽屉导航，以及加载、空数据和错误状态。

### 6.3 Dashboard

Dashboard 至少展示：

1. 已开放企业数；
2. 专科可投企业数；
3. 本科可投企业数；
4. 今日新增岗位数；
5. 当前用户已投递数量；
6. 当前用户面试数量；
7. 当前用户 Offer 数量；
8. 未来 14 天内即将截止岗位数；
9. 最近 7 天投递趋势；
10. 企业行业分布；
11. 最近 5 条投递记录。

统计口径应在界面或接口文档中保持一致。API 的“已开放企业”“专科/本科可投”“今日新增岗位”和“即将截止岗位”只统计 `is_demo = false` 且 `recruitment_status = open` 的记录。数值是当前本地已核验数据库的聚合，不得解释为全网市场规模；前端静态图表中的演示数字必须标明 Demo。

### 6.4 企业管理

- 创建、查看、修改和删除企业；
- 列表分页，页大小范围 1–100；
- 按企业名或工作城市搜索；
- 按行业、企业性质、学历、招聘状态、专科/本科可投和 Demo 标记筛选；
- 按名称、创建时间、截止日期排序；
- 保存官网、校招官网、Logo、招聘状态、日期、学历、专业、城市、来源、核验时间和 Demo 标记；
- 未找到资源返回 404。

### 6.5 岗位管理

- 创建、查看、修改和删除岗位；
- 列表分页，页大小范围 1–100；
- 按标题、描述或企业名称搜索；
- 按类别、城市、学历、企业、招聘状态和 Demo 标记筛选；
- 按标题、发布时间、截止时间、创建时间排序；
- 保存岗位描述、任职要求、投递链接、来源、核验时间和 Demo 标记；
- 创建岗位前验证关联企业存在。

### 6.6 求职记录

- 收藏：分页列表、新增和按岗位取消收藏；同一用户和岗位不重复收藏；
- 投递：分页、按状态/岗位筛选、排序、详情、新增、修改和删除，只允许用户操作自己的记录；
- 面试：分页、按状态筛选、排序和完整 CRUD，记录关联投递、面试类型、时间、状态、地点和备注；
- Offer：分页、按状态筛选、排序和完整 CRUD，记录关联投递、状态、薪酬文本、地点、收到日期、回复截止日期和备注；
- 通知：分页查询全部或仅未读通知，单条标记已读或全部标记已读。

### 6.7 数据与种子

- 提供至少 30 家企业和 60 个岗位；
- 覆盖 10 个行业：互联网、人工智能、通信、半导体、新能源、制造业、银行、央企国企、医药、物流；
- 所有种子企业与岗位必须满足：
  - `is_demo = true`；
  - `recruitment_status = demo_unverified`；
  - `data_source = demo_seed_not_realtime` 或同等明确值；
  - 名称或描述中出现 Demo 提示；
  - 不提供伪造的有效投递链接；
  - `last_verified_at` 为空，表示未进行真实核验。

## 7. 关键业务规则

1. 邮箱按小写形式保存并保持唯一。
2. JWT 的 `sub` 为用户 ID，令牌过期后必须重新登录。
3. 用户收藏、投递、面试、Offer 和通知均以当前认证用户为边界。
4. 企业删除时通过数据库级联删除其岗位；与岗位相关的业务记录应在实际删除前评估影响。
5. 所有业务时间以带时区时间存储，服务端统计以 UTC 计算，前端负责本地化展示。
6. Demo、已核验、已过期等状态必须可区分，未知状态不能默认显示为“开放”。
7. 用户在跳转到外部投递前，应看到来源与最后核验时间并自行复核。

## 8. 非功能需求

### 8.1 可用性

- 中文界面，信息层级清晰；
- 支持手机、平板和桌面宽度；
- 所有远程数据区域提供加载、空数据和错误反馈；
- 交互控件提供可识别的文本或 `aria-label`；
- 深色模式对比度可读。

### 8.2 性能

- 企业和岗位列表必须使用服务端分页，避免一次加载全部数据；
- 常用筛选和排序字段建立索引；
- 前端查询设置合理的 stale time 与有限重试；
- 后续可使用 Redis 缓存只读聚合结果，但第一阶段不依赖缓存才能正确运行。

### 8.3 安全

- 不在代码、镜像或文档中写死生产密钥；
- 密码使用现代密码哈希；
- 所有用户资源查询必须加入用户范围条件；
- CORS 仅允许配置的来源；
- API 输入使用 Pydantic 校验；
- 错误响应不得泄露密码哈希、数据库连接串或堆栈；
- 生产环境需要 HTTPS、密钥轮换、限流和更完善的会话机制。

### 8.4 可维护性

- TypeScript 开启严格模式；
- Python 公共函数和 API 代码包含类型标注；
- 模型变更必须带 Alembic 迁移；
- CI 执行 lint、类型检查、测试和前端构建；
- API 通过 OpenAPI 自描述，并维护人工语义文档。

### 8.5 数据合规

- 不将演示数据包装为实时数据；
- 不规避验证码、访问控制或反爬策略；
- 不未经授权复制受版权保护的完整职位描述；
- 接入真实来源前记录授权、来源 URL、采集时间和核验时间；
- 支持更正、下线与过期数据治理。

## 9. 第一阶段验收标准

### 9.1 启动

- `docker compose up --build` 可启动 frontend、backend、postgres、redis；
- 前端位于 `http://localhost:3000`；
- 后端位于 `http://localhost:8000`；
- Swagger UI 位于 `http://localhost:8000/docs`；
- PostgreSQL、Redis 和后端健康检查通过；
- 空数据库能够自动迁移并加载 30/60 演示数据。

### 9.2 功能

- 用户能注册、登录并读取当前用户；
- 未认证请求可读取企业和岗位，访问个人或写入 API 返回 401/403；
- 企业与岗位可完成 CRUD；
- 列表分页、搜索、筛选和排序参数有效；
- 当前用户可管理收藏、投递、面试、Offer 和通知；
- Dashboard 返回规定统计结构；
- 前端所有约定路由可访问，并在移动端可操作导航。

### 9.3 质量

- 前端 lint、类型检查和生产构建通过；
- 后端 Ruff、mypy 和 pytest 通过；
- 仓库不包含真实密钥、`.env`、嵌套 Git 仓库或未经声明的实时招聘数据；
- README 和六份专项文档可指导新开发者启动与验证项目。

## 10. 成功指标

第一阶段以工程和可用性指标为主，不使用演示数据计算业务成效：

- 新开发者能在 20 分钟内按文档启动 Docker 环境；
- 核心容器全部健康，核心 API 可通过 Swagger 完成验证；
- 注册—登录—浏览—收藏/投递—Dashboard 的关键路径无阻断错误；
- CI 对 `dev` 与 `main` 的变更稳定运行；
- 演示数据误识别为实时数据的已知入口为 0；
- 关键认证与 CRUD 接口具备自动化测试。

真实上线后再引入留存、任务完成率、截止提醒触达率、数据核验覆盖率等指标。

## 11. 风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 演示数据被误认为真实招聘 | 用户作出错误决策 | 多层 Demo 标记、无真实投递链接、来源与核验时间字段 |
| JWT 被浏览器脚本读取 | 会话被盗用 | 第一阶段减少第三方脚本；后续迁移 HttpOnly Cookie、加入 CSP 与会话撤销 |
| 删除企业造成关联数据丢失 | 历史记录不完整 | 生产化前引入软删除/归档与删除影响检查 |
| 外部数据过期 | 展示错误截止时间 | 核验状态、最后核验时间、TTL、到期自动降级为待核验 |
| 聚合统计变慢 | Dashboard 延迟 | 索引、查询分析、Redis 缓存和异步预聚合 |
| 测试数据库与 PostgreSQL 行为差异 | CI 未发现兼容问题 | 保留快速 SQLite 测试，并在后续加入 PostgreSQL 集成测试 |

## 12. 路线图

### Phase 2：流程完善

- [x] 全部前端核心业务页面与 API 深度联动；
- [x] 简历版本管理、本地附件存储和投递关联；
- [x] 岗位订阅、截止提醒、面试与 Offer 提醒；
- [x] 记录编辑、受控状态流转与个人审计；
- [x] PostgreSQL 集成测试和浏览器端到端测试。

第二阶段附件使用受认证 API 访问的本地持久卷，允许 PDF、DOC、DOCX，默认上限 10 MB。该方案适用于本地开发与单实例验证；对象存储、恶意文件扫描与异步调度仍属于生产化工作。

### Phase 3：可信数据能力

- [x] 仅允许登记已授权或可合法使用的数据源；
- [x] 本地 CSV 导入、字段标准化、企业/岗位去重、来源追踪和重新核验；
- [x] 本地管理员审核台与普通用户写权限隔离；
- [x] 数据质量、过期记录与来源覆盖率 Dashboard。

第三阶段导入能力仍保留，所有非 Demo 导入数据先进入 `unverified` 状态，管理员核验后才能成为开放记录。

### Phase 4：企业官方来源同步

- [x] 管理员逐个绑定企业官方招聘页或官方 Feed，并记录允许使用的依据；
- [x] 本地单进程调度、手动同步和运行历史；
- [x] HTML 链接、RSS、Atom、JSON Feed 解析及 URL 去重；
- [x] robots.txt、SSRF、超时、响应大小、批量上限与最低间隔保护；
- [x] 自动发现岗位保持待核验，岗位库提供新的官方投递链接入口。

第四阶段不承诺全网覆盖，不执行 JavaScript，不登录或绕过验证码，也不自动代表用户提交简历。每家企业必须由管理员根据其官方结构和条款单独配置。

### Phase 5：公开浏览与 GitHub 发布准备

- [x] 企业和岗位读取取消登录要求，个人与管理操作继续保护；
- [x] 首批 14 家企业、30 个正式项目或岗位具有官方链接和核验日期；
- [x] 过期、结束或官方显示零岗位的项目不进入开放列表；
- [x] 补充安全策略、贡献指南、Issue/PR 模板、Dependabot 和发布清单；
- [x] 访客默认入口调整为公开岗位库。

正式数据是 2026-07-16 的发布基线，不宣称覆盖全网。来源变化后需重新核验、关闭或更正。

### Phase 6：AI 辅助

- 在用户明确授权下分析简历与岗位匹配点；
- 生成可编辑的求职准备清单和复盘摘要；
- 所有 AI 输出标注模型生成、输入来源和不确定性；
- 不使用 AI 猜测企业是否招聘，也不替用户执行第三方投递。
